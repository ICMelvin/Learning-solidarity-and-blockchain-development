    * Blockchain Oracles are Services that feed external (off-chain) data into smart contracts.
    (Oracle Problem): Blockchains are deterministic and intentionally walled off thus they can't access outside data on their own. But smart contracts often need real-world data (prices, randomness, etc.)
     to function. That gap is the Oracle Problem.
    Solution: Oracles fetch and deliver verified off-chain data on-chain.
    Types: Price feeds, computational data, randomness (VRF), cross-chain.
    Security note: Oracles are a top DeFi attack surface — manipulation (e.g., via flash loans) is a common exploit

    Decentralized end-to-end — no single point of failure or trust
    Chain-agnostic — works across any blockchain

# How blockchain actually works
    ** A hash; is a unique fixed length string that identifies a peice of data {eg of hash algorithm includes(SHA256)}, to 
    create a hash, a peice of data is put into a hash function. ethereum uses (keccak-256 hash algorithm), the length of a 
    hash string length is constant no matter how big or small the data is. 

    ** {Went to a site called blockchain demo to discover the Difference btm hash, block, blockchain, distributed
    tokens, and coinbase}
   
    ** Block is Like a hash, it condenses data into a fixed-length string, but a block also includes a nonce.
    Nonce: A number miners search for to solve the block's computational puzzle (Proof of Work). Mining = repeatedly trying different nonces until one produces a valid hash (e.g., below a target difficulty).
    Core difference:

    Hash → hashes just the data
    Block → hashes three components: block number, nonce, and data
   
    * Blockchain is a collection of blocks, where each block adds one more field — previous hash (the hash of the block before it).
    Genesis block: The first block in the chain; its "previous hash" field is non-existent/null.
    How it hashes: Like a block, but now includes four components: block number, nonce, data, and the previous block's hash.
    Why it's immutable: Since each block's hash depends on the previous block's hash, altering any block changes its hash thus breaking the chain link and invalidating that block plus every block after it.

    * Distributed (Decentralized) this is when the same blockchain data is copied across many peers/nodes — each node holds an identical copy of the full chain.
    How it ensures integrity: If one node alters its data, that copy no longer matches the rest of the network — making it instantly identifiable as invalid.
    In short: Transactions aren't stored in one place; they're replicated across many interconnected nodes, and consensus among them determines what's valid and whats not.

    * A scalability problem in a blockchain is that a block can only hold a certain amount of transaction at a

# Asynchronous Programming in JavaScript

    * Synchronous programs execute code line by line — one task must finish before the next one begins (Start - finish - proceed).
    * Asynchronous programs can move on to other tasks while waiting for a slow task (like a network request) to finish.

    * Promises
        When an async task runs, it returns a Promise — which represents the eventual result of that task. A promise has 3 states:

       - pending — still running
       - fulfilled — completed successfully
       - rejected — failed

    * async / await
       - async marks the function as asynchronous
       - await pauses execution of that line until the promise resolves, then continues

   ## Note: Synchronous code does not return promises, Promises come from asynchronous operations, not synchronous ones.

    - >> this is the entire code explained
            
            // We import the `task` function from hardhat/config.
        // This function is used to define custom tasks that Hardhat can run from the CLI.
        import { task } from "hardhat/config";

        // We define a new task called "block-number" and export it so it can be
        // imported and registered in hardhat.config.ts via the `tasks` array.
        export const myNewTask = task(
        "block-number", // The task name — what you type in the CLI: `yarn hardhat block-number`
        "Prints the current block number", // Description — shows up when you run `yarn hardhat help`
        )
        .setInlineAction(
            // setInlineAction() is used for simple tasks where you want to define
            // the logic directly here instead of in a separate file.
            // It takes an anonymous async function with two parameters:
            // - taskArgs: any CLI arguments passed to the task (none in this case)
            // - hre: the Hardhat Runtime Environment — gives you access to everything
            //   Hardhat provides: network config, provider, plugins, and more.
            async (taskArgs, hre) => {
            // In Hardhat v3, you must explicitly connect to the network before
            // you can interact with it. hre.network.connect() establishes that
            // connection and returns a provider object.
            // The `provider` is your gateway to the blockchain — it lets you
            // send requests like getting block numbers, balances, transactions, etc.
            const { provider } = await hre.network.connect();

            // provider.request() sends a JSON-RPC request to the network.
            // "eth_blockNumber" is a standard Ethereum JSON-RPC method that
            // returns the latest block number as a hexadecimal string e.g "0x1a2b3c".
            const blockNumber = await provider.request({ method: "eth_blockNumber" });

            // blockNumber comes back as a hex string like "0x1a2b3c".
            // parseInt() with base 16 converts it to a regular number.
            // e.g parseInt("0x1a2b3c", 16) => 1715004
            console.log("Current block number:", parseInt(blockNumber, 16));
            },
        )
        // .build() finalizes the task definition and returns a task object.
        // Without this, the task is incomplete and can't be registered in the config.
        .build();

# Mocking & helper hardhat-config 

    - helper-hardhat-config.js is a separate configuration file that holds network-specific constants and metadata used across your deploy scripts. 
    Instead of hardcoding values like Chainlink price feed addresses or chain IDs directly in your deploy scripts, you centralize them here and import as needed. It typically contains:

       * networkConfig — maps chain IDs to network-specific values (price feed addresses, VRF coordinators, etc.)
       * developmentChains — list of local networks so deploy scripts know when to use mocks instead of real contracts
       * Mock constants — like DECIMALS and INITIAL_ANSWER for local mock deployments

        it Keeps your deploy scripts clean and makes adding new networks as simple as dropping a new entry in networkConfig.

    - Mocking in Hardhat is the practice of deploying fake versions of external contracts (like Chainlink price feeds) 
    on your local network since those real contract don't exist on hardhat or localhost.

       * MockV3Aggregator.sol — a fake Chainlink price feed contract you deploy locally that mimics the real one's interface
       * A mock deploy script (e.g. 00-deploy-mocks.js) — checks if you're on a development chain using developmentChains, and if so, deploys the mock instead of pointing to a real feed address
       * DECIMALS and INITIAL_ANSWER from your helper-hardhat-config.js — used as constructor args when deploying the mock to simulate a realistic price feed response

    The flow is: if local → deploy mock and use its address; if testnet/mainnet → grab the real price feed address from networkConfig. This lets you test your contracts fully offline without needing
    real network connections or spending testnet ETH.

# Storage in Solidity   
    - Storage is like a giant array or a giant list that keeps a list of all the variables we create.
    - Constant or immutable variables, they do not take up a slots in the storage  
    - Variables whos scope are within a function do not take up a slot in storage, thus they don't persist.
    - A persistent variable is a variable that gets written to storage
    - in order to make retrieving and storing variables take less gas than it normally does, you can add (load) it to memory, thus with this it does not repeadedly
         keep going to storage to read and store which costs gas 
    - Do not forget that mappings can't be loaded into memory, cause it's too wacky. do check out opcodes.
